# VS Code extension for StandUp Break

brief: Create `vscode-extension/` (repo root: /Users/sherif/Squat-Overflow) that behaves like the Chrome extension in `extension/`, reusing its code unchanged. Camera pages cannot run in VS Code webviews, so the VS Code extension host (Node) runs the unmodified `extension/service-worker.js` against a fake `chrome.*` object, and serves the unmodified pages (`break.html`, `trainer.html`, `popup.html`, `options.html` + JS/CSS/lib) from a local HTTP server on 127.0.0.1. A browser-side `chrome.*` shim is injected into every served HTML page. Break and practice pages open in the user's external browser (camera allowed on localhost). Dashboard (popup.html) and Settings (options.html) try VS Code's Simple Browser (`simpleBrowser.show`) and fall back to the external browser. A status-bar item shows the next-break countdown. Deliverable: working extension + `.vsix`.

gates: `cd /Users/sherif/Squat-Overflow/vscode-extension && node scripts/sync-web.mjs && node --test test/ && node ../extension/tests/check.mjs`

## Rules for all items

- Never edit anything under `/Users/sherif/Squat-Overflow/extension/`. It is the source of truth; copy, never fork.
- Host-side files are ESM `.mjs` (no TypeScript, no bundler, no runtime npm deps). Only `src/extension.js` is CommonJS and loads host code with `await import("./host/index.mjs")`.
- Only `src/extension.js` may `require("vscode")`. All of `src/host/*` and `test/*` must run in plain Node (>= 20) with injected adapters.
- Node 20 globals (`fetch`, `crypto.randomUUID`, `URL`) are assumed.
- No cookies. Auth = random token in the URL path prefix (see item 4), so it also works inside Simple Browser (an iframe).

## Design (decided, do not re-decide)

URL scheme: `http://127.0.0.1:<port>/<token>/<file>`. `<token>` = 24 random bytes hex, new per activation. All page-relative URLs (`theme.css`, `popup.js`, module imports) resolve under the prefix automatically. `chrome.runtime.getURL(p)` => `<baseUrl>/<p>` where `baseUrl = http://127.0.0.1:<port>/<token>`.

Windows: host-side `chrome.windows.create` records `{id, url}`, opens `url` with query `__wid=<id>` added (before any `#hash`; use `&` if a query exists), via the injected `openUrl`. A window counts as closed when (a) its page's SSE connection (`/__events?wid=<id>`) is gone for more than 4000 ms, (b) the page POSTs `/__api/close?wid=<id>`, or (c) no SSE connection for it appeared within 20000 ms of creation. Closing fires `chrome.windows.onRemoved` listeners with the id.

# Phase 2: open break/practice inside VS Code, with camera via ffmpeg

brief (phase 2): The user wants Break, Practice, Dashboard and Settings pages to open INSIDE VS Code (a WebviewPanel wrapping an iframe of the local server URL), not in the external browser, and the camera must work there. VS Code webviews deny getUserMedia, so the extension host captures the webcam with `ffmpeg` and streams MJPEG from the local server (`GET /<token>/__camera`). In editor mode the page shim replaces `navigator.mediaDevices.getUserMedia` with a function returning a `MediaStream` built from a canvas that draws that MJPEG stream, so `extension/lib/pose-client.js` and `extension/trainer.js` work unchanged. External-browser mode stays available via a setting and keeps the real camera.

gates (phase 2): same gates as above, with `node --test "test/*.test.mjs"`.

## Phase 2 design (decided, do not re-decide)

- Setting `standupBreak.openIn`: `"editor"` (default) | `"browser"`. `"editor"` opens every page (break, practice, dashboard, settings) in a WebviewPanel; `"browser"` keeps the current external-browser behaviour for break/practice and panels for dashboard/settings.
- Setting `standupBreak.ffmpegPath` (string, default `""` = auto) and `standupBreak.cameraDevice` (string, default `""`). Auto ffmpeg lookup order: setting, then `ffmpeg` on PATH, then `/opt/homebrew/bin/ffmpeg`, `/usr/local/bin/ffmpeg`, `/usr/bin/ffmpeg` (first that exists via `fs.existsSync`; for plain `ffmpeg` just try spawning it).
- ffmpeg args by `process.platform`: darwin `["-hide_banner","-loglevel","error","-f","avfoundation","-framerate","15","-video_size","640x480","-i", device||"0", "-f","mjpeg","-q:v","5","-"]`; linux same but `-f v4l2 -framerate 15 -video_size 640x480 -i device||"/dev/video0"`; win32 `-f dshow -framerate 15 -video_size 640x480 -i video=<device>` (device required; if empty, report error "Set standupBreak.cameraDevice to your camera name (ffmpeg -list_devices true -f dshow -i dummy)").
- Camera lifetime: ffmpeg starts when the first subscriber arrives, stops 2000 ms after the last one leaves. All subscribers share one process.
- Editor-mode page URL: the normal page URL plus query `__cam=1` (append with `&` if a `?` exists, else `?`; always before any `#hash`). The shim treats `__cam=1` (also persisted in `sessionStorage` key `__cam`, try/catch) as "camera comes from the host".
- Panels: one WebviewPanel per opened page, `enableScripts: false` is NOT acceptable to rely on; use `enableScripts: true`, `retainContextWhenHidden: true`, HTML = a full-bleed `<iframe>` with `src` = page URL, `allow="autoplay; clipboard-write"`, and a meta CSP `default-src 'none'; frame-src http://127.0.0.1:* http://localhost:*; style-src 'unsafe-inline';`. Panel mapping by window id: for URLs containing `__wid=<id>`, keep `Map<id, panel>`; panel `onDidDispose` calls `host.host.windowClosed(id)`; `chrome.windows.onRemoved` (via `host.chrome`) disposes the matching panel. Opening a URL whose wid already has a panel just reveals it.
